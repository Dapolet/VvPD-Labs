# Лабораторная работа № 3

**Строки, кодировки, Base64, регулярные выражения и URI**

Проект демонстрирует путь от байтов и кодовых точек до строк, регулярных
выражений, HTML-формы и разбора URI. Все эксперименты выполнены в WSL2
(Debian 13) с компилятором GCC 14.2.0, Python 3.13.5 и Node.js 20.19.2.

## Быстрый старт

```bash
make            # собрать C-программы и генератор
make strings    # только C-эксперименты
make regex      # пересоздать VPD_Lab3.txt и выполнить regex.py
make test       # запустить все демонстрации и selftest.js
```

Запуск по отдельности:

```bash
./strings/ascii
./strings/utf8
./strings/types
./strings/unicode_identifiers
python3 strings/encoding.py
python3 strings/base64_demo.py

cd regex
./generator > VPD_Lab3.txt     # stdout — только данные, статистика идёт в stderr
python3 regex.py
```

Веб-часть не требует сборки:

```bash
python3 -m http.server 8000
# http://localhost:8000/web/
```

Файл `web/index.html` работает и при открытии напрямую (`file://`).

## Этапы

### 1. ASCII: `sizeof` и `strlen`

`strings/ascii.c` печатает строку `Hello`, `sizeof(text) = 6`,
`strlen(text) = 5` и коды всех шести элементов, включая завершающий `'\0'`.
`sizeof` — размер объекта в байтах, `strlen` — число байт до первого нуля.

### 2. UTF-8

`strings/utf8.c` выводит `strlen`, `sizeof` и hex-байты для `Hello`,
`Привет`, `ёж`, `大学` и пяти пробелов. `strlen` считает байты, а не
графические символы: у `Привет` 12 байт и 6 кодовых точек, у `ёж` — 4 байта
и 2 кодовые точки. Дополнительно реализован подсчёт кодовых точек без
Unicode-библиотеки (по старшим битам байтов).

### 3. Одинаковые коды — разные типы

`strings/types.c` хранит коды `H e l l o` в массивах `char`, `short`, `int`
и `unsigned long long`. Все четыре массива печатают `Hello`, но занимают
5, 10, 20 и 40 байт. Массивы `short`/`int`/`unsigned long long` не являются
C-строками: их нельзя передавать в `printf("%s", ...)`.

### 4. `<stdint.h>`, `wchar_t`, wide strings

Там же: `CHAR_BIT = 8`, размеры обычных типов, наличие `uint8_t`…`uint64_t`,
`uint_least32_t` (4 байта) и `uint_fast32_t` (8 байт). `sizeof(wchar_t) = 4`
на Linux; `wcslen` считает единицы `wchar_t`, а не кодовые точки.
`wchar_t` — платформенно-зависимый целочисленный тип, а не «UTF-32 по
стандарту»: на Windows он 2-байтовый.

### 5. Кодировки и представления

`strings/encoding.py`:

- сравнивает UTF-8, UTF-32 LE и UTF-32 BE для пяти строк;
- показывает BOM `FF FE 00 00` в `encode("utf-32")` на little-endian системе;
- разбирает байт `0xB8`: в cp1251 это `ё`, а в UTF-8 одиночный `0xB8`
  некорректен (это продолжающий байт);
- доказывает различие кириллических `М`/`О` и латинских `M`/`O`
  (U+041C/U+041E против U+004D/U+004F);
- запускает Unicode-идентификаторы в Python;
- дополнительно: UTF-16 LE/BE и приблизительный подсчёт графемных кластеров.

`strings/unicode_identifiers.c` повторяет эксперимент с идентификаторами
в GCC. Технически Unicode-имена работают, но в командном проекте без
дополнительных правил нейминга их использовать не следует.

### 6. Base64

`strings/base64_demo.py` выполняет полный цикл
`大学 → UTF-8 (6 байт) → Base64 (5aSn5a2m) → байты → UTF-8`, показывает
padding `=`, URL-safe вариант (`+` → `-`, `/` → `_`), формулу
`4 × ceil(n / 3)`, накладные расходы (~33 %) и побайтовое восстановление
бинарного файла с совпадением SHA-256.

Base64 — кодирование бинарных данных в ASCII-текст. Оно не является
кодировкой Unicode и не заменяет UTF-8.

### 7. HTML-сущности

`strings/entities.html` показывает `ё`, `&#1105;` и `&#x451;` — три записи
одной кодовой точки U+0451. В исходном файле это разные байты, в браузере —
один и тот же символ.

### 8. Генератор контрольной строки

`regex/generator.c`:

- имя и фамилия латиницей: `Dmitrii Poletaev`;
- контрольная последовательность — десятичные ASCII-коды без разделителей:
  `68109105116114105105328011110810111697101118`;
- 100 000 случайных цифр;
- последовательность вставлена в начало, середину и конец;
- результат выводится одной строкой; статистика пишется в `stderr`.

```bash
cd regex
./generator > VPD_Lab3.txt
```

Размер файла — 100133 байта, последовательность встречается ровно 3 раза.

### 9. Регулярные выражения

`regex/regex.py`:

- считает `re.findall()` для `2^0 … 2^64` (всего 43 169 неперекрывающихся
  вхождений);
- удаляет степени двойки через `re.sub()` в порядке от `2^64` к `2^0`;
- сохраняет `VPD_Lab3_final.txt` (57 005 байт);
- демонстрирует, почему порядок удаления важен: `1` разрушает `128`;
- сравнивает обычный поиск с `(?=(...))` на шаблонах `1024`, `101`, `11`;
- дополнительно сравнивает `re.ASCII` и Unicode-режим для `\w`.

### 10. Веб-форма

`web/index.html` + `web/validation.js` проверяют ФИО, группу, телефон,
e-mail, дату и URI. Для группы используется шаблон
`/^М3О-\d{3}БВ-\d{2}$/u` с кириллическими `М` и `О`. Телефон — один
учебный формат `+7 (999) 123-45-67`. E-mail — упрощённое правило.
Дата проверяется сначала по форме `YYYY-MM-DD`, затем семантически через
`Date`, поэтому `2026-02-31` отклоняется.

На странице также показаны гомоглифы, разбор URI учебной регуляркой и
`new URL()`, `encodeURIComponent`/`decodeURIComponent` и сравнение
percent-encoding с HTML-сущностями и Base64.

Проверка без браузера:

```bash
node web/selftest.js
```

### 11. URI и нейминг

Для URI `https://example.org:8443/api/v1/student-profile?id=304&group=...`
выделены scheme, host, port, path, query и fragment. Штатный `URL`
дополнительно декодирует параметры (`group` → `М3О-304БВ-26`), тогда как
regex-разбор возвращает сырую строку запроса.

Плохие имена исправлены в отчёте: смешение языков и транслита
(`LK_employee`, `user_kabinet`, `lichnyKabinetEmployee`) заменено на
единую английскую систему, а URI приведён к REST-виду
`/api/employees/304/personal-account`.

## Переносимость

Проект проверен в WSL2 Debian 13 (GCC 14). На macOS он также собирается:
`make` использует системный `cc` (Apple Clang), нужны Xcode Command Line
Tools. Все C-файлы написаны на C17 без Linux-специфичных вызовов.

Отличия, которые могут проявиться на macOS:

- `sizeof(wchar_t)` и `uint_fast32_t` зависят от платформы; числа в отчёте
  относятся к Linux x86_64. На macOS `wchar_t` тоже 4 байта, но проверьте
  вывод `types.c`.
- `unicode_identifiers.c` — дополнительный эксперимент; UTF-8-идентификаторы
  требуют достаточно нового Apple Clang (15+). Если компилятор старый,
  собирайте только обязательные файлы.
- `web/selftest.js` и `python3` требуют установленных Node.js и Python 3;
  без Node цель `make test` пропускает selftest с сообщением.
- После `make regex` файл `VPD_Lab3.txt` генерируется случайно, поэтому
  количества вхождений отличаются от приведённых в отчёте.

## Замечания

- Байты `>= 0x80` при печати приводятся к `unsigned char`, иначе `char`
  может показать отрицательное число.
- `strlen` для UTF-8 — длина в байтах; для числа символов нужен разбор
  кодовых точек, а для графем — ещё и Unicode-алгоритм сегментации.
- `re.findall` не находит перекрывающиеся совпадения; для этого нужна
  опережающая проверка `(?=...)`, которая не потребляет символы.
- Регулярное выражение проверяет форму строки, но не смысл данных:
  существование даты, доступность URL или реальность e-mail проверяются
  отдельно.
- `VPD_Lab3.txt` генерируется случайно: после `make regex` числа в отчёте
  могут отличаться, потому что меняется входной поток.
