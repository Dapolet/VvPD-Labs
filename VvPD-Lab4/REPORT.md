## 3. Часть I. Указатели и адреса

### 3.1. Значение, адрес, указатель, разыменование

Фрагмент вывода `pointers/pointers`:

```text
value         = 304
&value        = 0x16f90e974
ptr           = 0x16f90e974
*ptr          = 304
value after *ptr = 305: 305
&ptr          = 0x16f90e978
sizeof(ptr)   = 8 байт
sizeof(value) = 4 байт
```

`ptr` и `&value` содержат один и тот же адрес, потому что `ptr` был
инициализирован выражением `&value`: указатель хранит адрес объекта
`value`. `&ptr` — это адрес самой переменной-указателя, то есть другого
объекта. Поэтому `&ptr` отличается от `&value`.

Разыменование `*ptr` обозначает объект, на который указывает `ptr`.
Присваивание `*ptr = 305` изменяет именно `value`, а не копию значения.
Указатель сам является объектом: у него есть собственный адрес `&ptr` и
собственный размер `sizeof(ptr) = 8` байт на arm64.

Адреса в выводе зависят от ASLR и текущего запуска; сравнивать нужно
именно отношения `ptr == &value` и `&ptr != &value`, а не конкретные
числа.

Указатель на указатель:

```text
pptr          = 0x16f90e978
*pptr         = 0x16f90e974
**pptr        = 305
```

Здесь `pptr` хранит адрес `ptr`, `*pptr` — значение `ptr` (адрес
`value`), а `**pptr` — само значение `305`.

### 3.2. Размеры указателей разных типов

```text
sizeof(char *)   = 8
sizeof(int *)    = 8
sizeof(double *) = 8
sizeof(void *)   = 8
```

На этой платформе все указатели занимают 8 байт. Это наблюдение, а не
универсальное правило: стандарт C не требует, чтобы указатели разных
типов имели одинаковый размер. На других архитектурах возможны иные
соотношения.

### 3.3. Массив и указатель

Вывод `pointers/arrays`:

```text
sizeof(a)       = 20 байт
sizeof(a[0])    = 4 байт
sizeof(&a[0])   = 8 байт
sizeof(&a)      = 8 байт
number of items = 5
```

`sizeof(a)` измеряет весь массив из пяти `int`: 5 × 4 = 20 байт.
`sizeof(&a[0])` измеряет указатель на первый элемент, а
`sizeof(&a)` — указатель на весь массив `int[5]`. Это разные объекты,
хотя оба указателя имеют размер 8 байт.

В обычных выражениях имя массива преобразуется в указатель на первый
элемент. Исключения — `sizeof`, `&` и инициализация строкового литерала.
Поэтому `a[i]` и `*(a + i)` обращаются к одному и тому же элементу:

```text
i=0  a[i]=10  *(a+i)=10  &a[i]=0x16f60e948  a+i=0x16f60e948
i=1  a[i]=20  *(a+i)=20  &a[i]=0x16f60e94c  a+i=0x16f60e94c
...
```

Адреса соседних элементов отличаются на 4 байта — на `sizeof(int)`.
Указатель `p + 1` переходит к следующему объекту типа `int`, а не
увеличивает числовой адрес на один байт. Соответственно:

```text
second - first = 1 (в элементах int)
(char *)second - (char *)first = 4 байт
&a + 1 = 0x16f60e95c
(char *)(&a + 1) - (char *)&a = 20 байт
```

`&a + 1` переходит через весь массив из 20 байт, потому что тип
`&a` — указатель на `int[5]`.

## 4. Часть II. Динамическая память в C

### 4.1. `malloc`, `calloc`, `realloc`, `free`

Вывод `pointers/dynamic`:

```text
size = 10, capacity = 16
data = 0 1 4 9 16 25 36 49 64 81

malloc block at 0x600002235220: содержимое не читаем (значения не определены)
calloc block at 0x600002235240: все 5 значений равны нулю: yes
```

`malloc(n * sizeof *data)` удобнее, чем повторное указание типа:
если тип `data` изменится, выражение `sizeof *data` автоматически
подстроится. Например, для `int *data` это `sizeof(int)`, для
`double *data` — `sizeof(double)`.

`malloc` не инициализирует память. Читать неинициализированные значения
нельзя: это неопределённое поведение. В демонстрации содержимое
`malloc`-блока не читается. `calloc` заполняет выделенную область
нулевыми байтами; для массива целых это даёт нули. Но нулевые байты
нельзя считать универсальным «нулевым значением любого типа»: например,
для указателей и чисел с плавающей точкой представление всех нулевых
байтов не обязано совпадать с их нулевым значением.

Рост массива:

```c
if (vector->size == vector->capacity) {
    size_t new_capacity = vector->capacity ? vector->capacity * 2 : 4;
    int *temporary = realloc(vector->data,
                             new_capacity * sizeof *temporary);
    if (temporary == NULL)
        return false;
    vector->data = temporary;
    vector->capacity = new_capacity;
}
```

Ёмкость удваивается: 4 → 8 → 16. При 10 элементах получается
`capacity = 16`.

Опасный вариант:

```c
data = realloc(data, new_size);
if (data == NULL) {
    /* старый адрес потерян */
}
```

Если `realloc` не смог выделить новый блок, он возвращает `NULL`, а
старый блок остаётся выделенным. Прямое присваивание уничтожает
единственную копию адреса старого блока — возникает утечка. Безопасно
использовать временный указатель, как в коде выше.

### 4.2. `goto cleanup`

В `read_sum()` ресурсы освобождаются в одной точке:

```c
int result = 1;
FILE *file = NULL;
int *buffer = NULL;

file = fopen(path, "r");
if (file == NULL)
    goto cleanup;

buffer = malloc(limit * sizeof *buffer);
if (buffer == NULL)
    goto cleanup;

/* полезная работа */
result = 0;

cleanup:
    free(buffer);
    if (file != NULL)
        fclose(file);
    return result;
```

Вывод:

```text
process_file: read 5 values, sum = 30
read_sum(existing) = 0
read_sum(missing)  = 1 (очистка всё равно выполнена)
```

При ошибке открытия файла управление переходит в `cleanup`, где
`free(NULL)` допустим и ничего не делает, а `fclose` вызывается только
для открытого файла. `goto` здесь ограничен одной точкой очистки; это
не превращает его в средство произвольных переходов внутри алгоритма.

### 4.3. Типичные ошибки управления памятью

| Ошибка | Нарушенное правило | Как исправить |
|---|---|---|
| Утечка памяти (memory leak) | выделенный блок потерян, `free` не вызван | хранить один адрес на блок; освобождать до перезаписи указателя |
| Висячий указатель (dangling pointer) | указатель ссылается на объект, время жизни которого закончилось | после `free` не использовать указатель; локально `p = NULL` |
| Использование после освобождения (use-after-free) | обращение к памяти после `free` | не разыменовывать освобождённый блок; пересмотреть владение |
| Повторное освобождение (double free) | один блок передан `free` дважды | один владелец; после `free` `p = NULL`; не копировать владение |
| Выход за границы (out-of-bounds) | индекс вне `0..n-1` | проверять индексы; в C++ использовать `at()`/контейнеры |
| Неинициализированный или нулевой указатель | разыменование мусора или `NULL` | инициализировать `NULL`, проверять перед разыменованием |
| Потеря указателя при `realloc` | результат `realloc` сразу записан в единственный указатель | использовать временный указатель |

Дополнительно: `free(NULL)` безопасен и ничего не делает. Установка
`p = NULL` после `free(p)` — локальная защитная мера; если на тот же
блок ссылались `p` и `q`, то `q` всё равно остаётся висячим.

## 5. Часть III. Динамическая память в C++

### 5.1. `new`/`delete` и `new[]`/`delete[]`

Вывод `cpp_memory/new_delete`:

```text
*value = 304
value after delete = nullptr

sum of 0,1,4,9,16 = 30

Student::Student()
student->id = 304
Student::~Student()

malloc returned 0x60000169c040 (raw memory, no constructor)

allocation failed: std::bad_alloc
nothrow allocation succeeded

sizeof(Student) = 4
```

`new int(304)` не только выделяет память, но и создаёт объект. Для
пользовательского типа `Student` вызывается конструктор, а `delete` —
деструктор. `new[]` создаёт массив объектов, поэтому освобождать его
нужно `delete[]`; смешивать `new[]` с `delete` или `new` с `free`
нельзя — это неопределённое поведение.

`malloc(sizeof(Student))` даёт сырую память, но не вызывает
конструктор. Для типа с нетривиальным конструктором это принципиально.

Обычная форма `new` при неудаче выбрасывает `std::bad_alloc`. Форма
`new (std::nothrow)` возвращает `nullptr`. В демонстрации обе формы
показаны; для `bad_alloc` используется нижний `operator new` с заведомо
невозможным размером, чтобы не просить у системы реальный гигантский
блок.

### 5.2. RAII

Вывод `cpp_memory/raii`:

```text
size = 5, capacity = 5, sum = 30
after push_back: size = 6, capacity = 10

*value = 304
after move: original = null, owner = 304

FileHandle: opened raii_demo.txt
FileHandle: closed in destructor

scope ended: vector, unique_ptr and FileHandle released automatically
```

`std::vector<int>` владеет динамическим массивом и освобождает его в
деструкторе. `std::unique_ptr<int>` — единственный владелец; после
`std::move` исходный указатель становится `nullptr`, а новый владелец
получает объект. `FileHandle` инкапсулирует `FILE *` и закрывает файл
в деструкторе, даже если из области выйти по `return` или исключению.

Это и есть RAII: получение ресурса есть инициализация, а время жизни
ресурса связано со временем жизни объекта. В современном C++ контейнеры
и умные указатели обычно предпочтительнее ручных `new`/`delete`.
`std::shared_ptr` нужен только при совместном владении; он не является
заменой `std::unique_ptr` по умолчанию.

## 6. Часть IV. Структуры и пользовательские типы

### 6.1. Формы определения

В `structs_files/structs.c` показаны все шесть форм:

1. предварительное объявление `struct Person;`;
2. именованная структура `struct Person { ... };`;
3. структура с одновременным объявлением переменной `} tom_employee;`;
4. анонимная структура с переменной `anonymous_tom`;
5. анонимная структура с `typedef` — `PersonT`;
6. именованная структура с `typedef` — `NamedPerson`.

`typedef` не создаёт новую структуру, а даёт существующему типу
дополнительное имя. В C тип `struct Person` уже существует; `PersonT`
или `NamedPerson` — удобные псевдонимы.

Инициализация:

```c
struct Person a = {"Tom", 38};
struct Person b = {
    .name = "Bob",
    .age = 41
};
```

Вторая форма — designated initializer, инициализация по именам полей.
Она удобна, когда полей много или порядок полей не должен быть скрытой
зависимостью.

### 6.2. Операторы `.` и `->`

```text
p->name = Tom, p->age = 38
(*p).age = 38
p->age and (*p).age denote the same field: 38 == 38
p == &a: yes
```

`p->age` эквивалентно `(*p).age`: сначала выполняется разыменование,
затем доступ к полю. Оператор `->` просто объединяет эти две операции.

### 6.3. Заполнение и выравнивание

Вывод:

```text
sizeof(struct Example) = 12
sum of field sizes = 6
offsetof(a) = 0
offsetof(b) = 4
offsetof(c) = 8

sizeof(struct Compact) = 8
offsetof(b) = 0
offsetof(a) = 4
offsetof(c) = 5
```

`struct Example { char a; int b; char c; }`:

```text
смещение 0:  char a
смещение 1:  padding (3 байта)
смещение 4:  int b
смещение 8:  char c
смещение 9:  tail padding (3 байта)
итого:       12 байт
```

Сумма размеров полей — 6 байт, но компилятор добавляет внутреннее
заполнение, чтобы `int b` был выровнен по границе 4 байта, а размер
всей структуры был кратен выравниванию самого строгого поля. Если
переставить поля:

```c
struct Compact { int b; char a; char c; };
```

получается 8 байт: `b` занимает 0–3, `a` — 4, `c` — 5, затем 2 байта
tail padding. Порядок полей может влиять на размер структуры.

`offsetof` из `<stddef.h>` показывает смещения полей. Конкретные
размеры и выравнивания зависят от ABI; для переносимого кода нельзя
жёстко предполагать 12 или 8 байт. `#pragma pack` может уменьшить
размер, но способен привести к невыровненному доступу, падению
производительности или аппаратным исключениям на некоторых
архитектурах.

`struct Person` с `char name[64]` и `int age` занимает 68 байт:
64 + 4, без дополнительного заполнения, потому что выравнивание
структуры — 4.

## 7. Часть V. Работа с файлами

### 7.1. Текстовый файл

Вывод `structs_files/text_file`:

```text
записано 5 строк в artifacts/numbers.txt
line: 0
line: 1
line: 4
line: 9
line: 16

read 5 numbers, sum = 30
```

Файл открывается на запись `"w"`, в него через `fprintf` пишутся
квадраты чисел, затем файл закрывается. После повторного открытия
`"r"` строки читаются через `fgets` с ограничением размера буфера;
`strtol` разбирает числа, сумма равна 30. Проверяются ошибки `fopen`,
`fprintf`, `fgets`, `fclose`.

### 7.2. Бинарный файл

Вывод `structs_files/binary_file`:

```text
sizeof(Student) = 72, records = 3
fwrite: written = 3
file size = 216 bytes, expected = 216 bytes
fread: got = 3
  1 | Ivan Ivanov      | 304
  2 | Anna Petrova     | 304
  3 | Petr Sidorov     | 305
round-trip fields match: yes
```

`fwrite` и `fread` работают с элементами заданного размера. Для трёх
записей по 72 байта получается 216 байт. Поля после чтения совпадают.
Файл открывается в бинарном режиме `"wb"`/`"rb"`, чтобы избежать
преобразования переводов строк.

### 7.3. Ловушка: указатель внутри структуры

```text
sizeof(StudentPtr) = 16
offsetof(name) = 8
student.name = 0x102bfbc28
file contains 16 bytes; dump:
00000000  01 00 00 00 00 00 00 00 28 bc bf 02 01 00 00 00  |........(.......|
pointer bits in file = 0x0000000102bfbc28
original pointer    = 0x102bfbc28
the string bytes themselves are not stored by fwrite
```

Структура `StudentPtr { uint32_t id; char *name; }` содержит `id`
(4 байта), затем 4 байта заполнения, затем указатель `name` (8 байт).
В файл попадает числовое значение указателя — адрес строки в памяти
текущего процесса, а не сама строка. В hexdump видны байты адреса
`28 bc bf 02 01 00 00 00`; строки `"Ivan Ivanov"` в файле нет.

После завершения программы и повторного запуска адрес почти наверняка
бессмыслен: ASLR и раскладка памяти меняются. Читать такой указатель
из файла и разыменовывать его нельзя — это неопределённое поведение.

Структура с массивом:

```text
sizeof(StudentFixed) = 68
offsetof(name) = 4
loaded.id = 2, loaded.name = "Anna Petrova"
```

Здесь строка хранится внутри структуры (`char name[64]`), поэтому она
попадает в файл и читается обратно.

### 7.4. Почему бинарный снимок структуры не является универсальным форматом

На результат влияют:

- заполнение (padding) и выравнивание (alignment);
- порядок байтов (endianness);
- размеры и представление типов;
- изменение структуры между версиями программы;
- наличие указателей и других адресно-зависимых полей;
- различия ABI и компиляторов.

Бинарная запись структуры удобна как учебный эксперимент, но
переносимый формат нужно проектировать явно: фиксировать ширину полей,
порядок байтов, способ хранения строк (длина + байты), версию формата
и, при необходимости, контрольную сумму. Ещё лучше сериализовать поля
по одному, а не записывать сырой снимок структуры.

## 8. Часть VI. Числа с фиксированной точкой

### 8.1. `0.1 + 0.2`

```text
0.1 + 0.2 in double = 0.30000000000000004 (equal to 0.3: no)
```

Двоичное представление `double` не хранит десятичные дроби точно:
`0.1` и `0.2` — бесконечные двоичные дроби, округлённые до 53 бит
мантиссы. Поэтому их сумма не равна точно `0.3`. Для денег это
неприемлемо, если нужна точная десятичная арифметика.

### 8.2. Денежный тип `Money`

`Money` хранит `int64_t raw` в сотых долях: `raw = 12345` означает
123.45.

```text
a = 123.45 (raw = 12345)
b = 0.55 (raw = 55)
a + b = 124.00 (raw = 12400)
a - b = 122.90 (raw = 12290)
-5.05 = -5.05 (raw = -505)
a * 3 = 370.35 (raw = 37035)
parse("-12.34") = -12.34 (raw = -1234)
parse("12.345") accepted: no
money(0.1) = 0.10 (raw = 10)
money(0.2) = 0.20 (raw = 20)
money(0.1) + money(0.2) = 0.30 (raw = 30)
```

Сложение и вычитание выполняются над `raw`, то есть над целыми
сотыми. Умножение на целое также остаётся в масштабе 100. Если
умножать два значения `Money`, масштаб промежуточного результата
станет 10000, и его нужно явно делить на 100 с выбранным правилом
округления. Переполнение `int64_t` тоже нужно проверять: диапазон
`raw` ограничен.

`money_parse` разбирает десятичную запись точно и отвергает больше
двух дробных цифр (`12.345`). Печать отрицательных значений
обрабатывает `INT64_MIN` через модуль без переполнения.

### 8.3. Q16.16

Q16.16 хранит 16 бит целой части и 16 бит дробной в `int32_t`.
Точность — 1/65536 ≈ 0.0000152588. Диапазон:

```text
минимум: -32768.0
максимум:  32767.999984741
```

Вывод:

```text
double     0.0000 -> raw=0 (0x00000000), value=0.000000000
double     1.0000 -> raw=65536 (0x00010000), value=1.000000000
double    -1.0000 -> raw=-65536 (0xffff0000), value=-1.000000000
double     0.1000 -> raw=6554 (0x0000199a), value=0.100006104
double     0.2000 -> raw=13107 (0x00003333), value=0.199996948
double     1.5000 -> raw=98304 (0x00018000), value=1.500000000
double 32767.9999 -> raw=2147483641 (0x7ffffff9), value=32767.999893188
double 32768.0000 -> raw=2147483647 (0x7fffffff), value=32767.999984741
double -32768.0000 -> raw=-2147483648 (0x80000000), value=-32768.000000000
double -32769.0000 -> raw=-2147483648 (0x80000000), value=-32768.000000000

Q16(0.1) = raw=6554 (0x0000199a), value=0.100006104
Q16(0.2) = raw=13107 (0x00003333), value=0.199996948
Q16(0.1) + Q16(0.2) = raw=19661 (0x00004ccd), value=0.300003052
Q16(0.3) = raw=19661 (0x00004ccd), value=0.300003052
Q16(1.5) * Q16(2.0) = raw=196608 (0x00030000), value=3.000000000
```

Значения `0.1` и `0.2` не представимы точно, но после округления до
Q16.16 их сумма совпадает с Q16.16-представлением `0.3`. Это не
«магия»: оба слагаемых и `0.3` округляются в одну и ту же сетку
1/65536. В общем случае ассоциативность и дистрибутивность могут
нарушаться; для денег лучше масштаб 100 или явная десятичная
арифметика.

При выходе за диапазон преобразование насыщает значение:
32768 → `INT32_MAX`, −32769 → `INT32_MIN`. Это осознанное решение;
альтернатива — возвращать ошибку.

## 9. Часть VII. Связное десятичное число

Вывод `linked_number/linked_number`:

```text
source: 304159265358979323846264338327950288419716939937510
forward: 304159265358979323846264338327950288419716939937510
backward: 015739939617914882059723833462648323979853562951403
length = 51, digit sum = 246

sizeof(Digit) = 24 bytes
payload per digit = 1 byte(s)
nodes = 51, total node bytes = 1224
contiguous payload would be 51 byte(s)

after push_front(9), push_back(2):
forward: 93041592653589793238462643383279502884197169399375102
length = 53

after free: head = 0x0, tail = 0x0, length = 0
second decimal_free is safe: head = 0x0, length = 0
```

Каждая цифра — отдельный узел:

```c
typedef struct Digit {
    uint8_t value;
    struct Digit *prev;
    struct Digit *next;
} Digit;
```

На arm64 `sizeof(Digit) = 24`: 1 байт значения, 7 байт заполнения,
8 байт `prev`, 8 байт `next`. Для 51 цифры занято 1224 байта только
под узлы, не считая служебных данных аллокатора; полезная нагрузка —
51 байт. Обход — это переходы по указателям, то есть «погоня за
указателями» с плохой локальностью и возможными промахами кэша.

Связный список удобен как учебная структура и для операций вставки,
но для BigUInt он проигрывает непрерывному массиву limb: массив
даёт последовательный доступ, лучшую локальность и меньшее число
выделений памяти.

## 10. Часть VIII. BigUInt на непрерывном массиве блоков

### 10.1. Представление

```c
typedef struct {
    uint32_t *limbs;
    size_t size;
    size_t capacity;
} BigUInt;
```

`limbs[0]` — младшие 32 бита, `limbs[size - 1]` — старшие. Ноль
представлен как `size == 0`. `capacity` — текущая ёмкость массива;
`size` — число значимых блоков.

Реализованы:

```text
biguint_init
biguint_free
biguint_reserve
biguint_normalize
biguint_from_u64
biguint_from_hex
biguint_copy
biguint_compare
biguint_is_zero
biguint_add
biguint_sub
biguint_mul
biguint_mul_u64
biguint_pow2
biguint_to_u64
biguint_bit_length
biguint_divmod_u32
biguint_print_hex
biguint_print_dec
```

`biguint_reserve` использует `realloc` через временный указатель и
зануляет новую часть массива. `biguint_normalize` удаляет нулевые
старшие блоки. Остальные операции принимают `result` отдельно от
операндов и поддерживают случай `result == left` или `result == right`:
сумма/разность/произведение считаются во временном массиве, после чего
старый массив `result` освобождается.

### 10.2. Сложение

```c
uint64_t sum =
    (uint64_t)a->limbs[i] +
    (uint64_t)b->limbs[i] +
    carry;

result->limbs[i] = (uint32_t)sum;
carry = sum >> 32;
```

Для суммы двух 32-битных блоков и переноса удобно использовать
`uint64_t`: максимум равен `(2^32 − 1) + (2^32 − 1) + 1 = 2^33 − 1`,
что помещается в 64 бита. Младшие 32 бита записываются в результат,
старшие — перенос в следующий блок. Если использовать `uint32_t`,
перенос будет потерян.

### 10.3. Вычитание

Вычитание разрешено при `a >= b`. Для каждого блока:

```text
subtrahend = b[i] + borrow
если a[i] >= subtrahend:
    result[i] = a[i] - subtrahend
    borrow = 0
иначе:
    result[i] = a[i] + 2^32 - subtrahend
    borrow = 1
```

Заём переходит в следующий блок. Если `a < b`, функция возвращает
`false` и не пытается представить отрицательное число.

### 10.4. Умножение

Школьное умножение O(n²):

```c
uint64_t current =
    (uint64_t)temporary[i + j] +
    (uint64_t)left->limbs[i] * right->limbs[j] +
    carry;

temporary[i + j] = (uint32_t)current;
carry = current >> 32;
```

Произведение двух 32-битных блоков, плюс существующее значение, плюс
перенос, максимум равно `(2^32 − 1)^2 + (2^32 − 1) + (2^32 − 1) =
2^64 − 1`, поэтому `uint64_t` достаточно. Результат имеет
`left->size + right->size` значимых блоков; в реализации выделяется
на один блок больше для безопасности, затем вызывается нормализация.

## 11. Часть IX. Выбор размера разрядного блока

Для 4096 бит:

| Тип блока | Блоков для 4096 бит | Особенности |
|---|---:|---|
| `uint16_t` | 256 | больше элементов, переносов и обращений к памяти |
| `uint32_t` | 128 | удобно: произведение 32×32 помещается в `uint64_t` |
| `uint64_t` | 64 | меньше элементов; для полного произведения 64×64 нужен 128-битный промежуточный тип |

Меньше блоков — не всегда автоматически быстрее: результат зависит от
архитектуры, компилятора, числа операций и характера доступа к памяти.
Для умножения `uint32_t` особенно удобен, потому что 32×32 помещается
в стандартный `uint64_t`. Для `uint64_t` может понадобиться
`unsigned __int128`, который является расширением GCC/Clang, а не
требованием стандарта C.

## 12. Часть X. Измерение производительности

### 12.1. Методика

`bigint/benchmark.cpp` сравнивает `uint16_t`, `uint32_t`, `uint64_t`

Параметры:

### 12.3. Интерпретация

На этой машине `uint64_t` быстрее всего: для 4096 бит нужно 64 блока
вместо 128 у `uint32_t` и 256 у `uint16_t`. При `-O0` отношение
времени `uint16`/`uint64` для сложения примерно 2338/608 ≈ 3.8, что
близко к отношению числа блоков 4. При `-O2` разрыв больше
(551/101 ≈ 5.5), потому что компилятор лучше оптимизирует цикл с
меньшим числом итераций и меньшим объёмом данных.

Удвоение при `-O2` заметно быстрее сложения: 70.67 нс/оп для `uint64`
против 100.72 нс/оп. Это ожидаемо: при удвоении не нужно читать второй
массив, меньше нагрузка на память.

Вывод «uint64 всегда лучше» делать нельзя. На другой архитектуре,
при другой структуре данных или для умножения с 128-битным
промежуточным результатом картина может измениться. Кроме того,
измерение включает обновление `volatile`-приёмника, чтобы компилятор
не выбросил вычисления; это небольшая, но постоянная добавка.

## 15. Выводы

В работе пройден путь от адреса и указателя до собственного
представления большого числа:

- указатель хранит адрес объекта и сам является объектом;
- массив и указатель различаются, но `a[i]` эквивалентно `*(a + i)`;
- `malloc`/`calloc`/`realloc`/`free` требуют дисциплины владения;
  безопасный `realloc` и `goto cleanup` уменьшают число ошибок;
- в C++ RAII, `std::vector` и `std::unique_ptr` заменяют ручное
  управление ресурсами;
- структуры имеют padding/alignment, а бинарный снимок структуры не
  является переносимым форматом;
- фиксированная точка даёт точную десятичную арифметику для денег и
  предсказуемую точность Q16.16;
- двусвязный список цифр наглядно показывает цену отдельных выделений
  памяти и переходов по указателям;
- BigUInt на непрерывном массиве `uint32_t` поддерживает сложение,
  вычитание, умножение и степени двойки с проверкой граничных случаев;
- производительность зависит от размера limb, оптимизации и памяти;
  измерения нужно повторять и анализировать статистику, а не делать
  вывод по одному запуску.

Все пункты 1–21 обязательного задания выполнены.
